# BUG B — exercises leak across topic boundaries

Written **before** any code change, 2026-09-20. Investigation only; the fix is
described in the last section and lives in the same commit.

## Symptom

Inside the journey, a kid working on one topic is served exercises whose
*content* belongs to a different topic — or to no topic at all. Reported
2026-09-15 (grade א "צורות" served a numeric-sequence story; grade ג "כפל
וחילוק" served a bare number-line question) and still reproducible.

## What it is NOT (each ruled out with evidence)

| Hypothesis | Verdict | Evidence |
|---|---|---|
| Serving returns rows from the wrong topic | **No** | `find_reusable_exercise` read from the live DB: `e.topic_id = p_topic_id`, or (`e.topic_id is null` and legacy topic string matches). The legacy clause requires `topic_id is null`, so tagged rows cannot collide by string. |
| Rows are mis-tagged or untagged | **No** | 1,036 exercises, **0** with `topic_id IS NULL`. Distinct topic ids per subject+grade equal the topic list exactly (Hebrew א4/ב3/ג6, math א6/ב7/ג9). |
| The client sends a grade that doesn't match the topic | **No, in the journey** | `getTopics(subject, grade)` feeds both the map and the grade that is sent, so they agree by construction. (The fallback below still exists for free-practice/legacy callers.) |
| Two topic ids share a curriculum string and collide | **No** | Same as row 1: the legacy match only applies to untagged rows. |
| The arithmetic safety gate / verdict-first evaluation | **No** | Those act on *feedback text* after an answer. The leak happens before an exercise exists on screen. Nothing in this fix touches them. |

## What it IS

Every row is **correctly tagged** with the topic it was asked for, but its
**content is not about that topic**. Tag correctness was never the same thing
as topical membership, and nothing in the system checks the second one.

### Evidence (live bank, read-only queries)

- The blatant class — a `fill_in_blank` whose question is *only* a computation
  ("כמה זה A ⊕ B?") — is legitimate in the six arithmetic topics (plus multiplication/division for
  × and ÷) and a leak everywhere else. **15 such rows** in topics that are not about arithmetic:
  `math-a-time` 6 of 7, `math-g-gematria` 3 of 5, `math-b-time` 2 of 2, and
  one each in `math-a-data`, `math-b-length`, `math-b-volume`, `math-g-area`.
- Real examples served today:
  - `math-a-time` (measuring time): **"כמה זה 15 - 7 + 4?"**
  - `math-g-gematria`: **"כמה זה 5 + 3?"**, **"כמה זה 5 + 2?"** (first-grade
    arithmetic inside a third-grade gematria topic)
  - `math-g-area`: **"כמה זה 12 × 8?"**
  - `math-a-data`: "בכיתה שלנו יש 5 ילדים שנולדו בחודש ינואר. היכן נמצא המספר 5
    על הציר?" — a data-flavoured sentence attached to a number-line skill.
- Frequency. At ~30 rows per topic and, e.g., 6 bare computations among the
  `math-a-time` rows, a uniform draw hits one about 1 time in 5, so a kid
  doing five exercises in that topic meets one with probability ≈ 67%
  (`1 − 0.8^5`; ignores the level split and the attempted-exercise exclusion,
  so it is an estimate, not a measurement). This is a high-frequency trust
  bug, not a rare edge.
- The arithmetic topics themselves are scope-consistent (no multiplication in
  grade א, operands inside 100 / 1,000 / 10,000). One face of the bug, not two.

## Mechanism — three links, all required

1. **The template is chosen without regard to the topic.**
   `generateExercise` picks the subtype with `pickSubtype(subject, grade)`,
   independent of the topic, then stamps the result with the requested topic
   (`topic: resolvedTopic.topic, topicId: resolvedTopic.id`). A generic
   numeric template (fill-in, number line, sequence, grouping) asked to
   produce content for "measuring time" can — and does — satisfy the template
   with bare numbers.
2. **Admission checks internal consistency, never topical fit.**
   `bank-guard.ts` verifies that an exercise's arithmetic and answer agree. Its
   own header documents the blind spot: a row "correctly tagged
   math-a-geometry but asking 'where is 42 on the line' passes every check".
3. **Serving trusts the tag.** `findReusableExercise` filters by `topic_id`,
   which is correct *as a tag* and says nothing about content.

### Why the 2026-09-15 fix (`cd8b103`) did not close it

- It changed the **prompt** for future generations: an instruction the model
  may or may not follow, verified by nothing in code.
- It **regenerated only the two reported topics**: `math-a-geometry` and
  `math-g-multiplication-division` each hold exactly 30 rows, all created at
  `2026-09-15 11:43:51 UTC`, none from the 09-14 seed (replaced, not
  supplemented). Those read as genuinely on-topic now.
- The other **33 topics — 976 of 1,036 rows (94.2%) — are the original
  2026-09-14 seed**, generated by the old prompt and never audited.
- Its regression test is a live-DB test that skips without a password, and by
  its own header "wouldn't have caught BUG B's real cause". So the suite has
  never been able to fail on this bug.

## Fix (root: give "belongs to this topic" a definition in code)

New `lib/exercises/topic-fit.ts`: for each topic, what its exercises must
contain, sourced from the Ministry's own curriculum wording rather than
invented — vocabulary for content topics (geometry, length, time, data, area,
volume, gematria), and an explicit "bare arithmetic is on-topic here" for the
arithmetic topics. Enforced at three points:

1. **Admission** (`generateExercise`): a draft that doesn't fit is rejected
   and re-requested with a corrective hint, inside the existing three-attempt
   retry loop; if the last attempt still doesn't fit the request throws
   (`TopicFitError`) rather than returning — and so never saving — a leaking
   row. It runs after every existing gate, including the arithmetic one, and
   changes none of them.
2. **Serving** (`findReusableExercise`): rows that don't fit are filtered out of
   the candidate page. This protects kids *now*, from the 976 unaudited rows,
   without any write to the production database.
3. **Audit** (`scripts/audit-topic-fit.ts`, read-only): lists every bank row
   that fails, so the offenders can be reviewed and deleted deliberately.

### Deliberately NOT covered — stated so it isn't mistaken for solved

- **Hebrew topics (13 of 35) are not checked.** Their subject is language
  skills with no reliable, code-checkable vocabulary; a wrong anchor list would
  reject good exercises. The evidence gathered here found the leak in math.
  Whether Hebrew topics leak *between each other* is unmeasured.
- **The check is vocabulary-based.** It catches "no topic content at all",
  which is the demonstrated failure. It cannot tell an exercise that mentions
  triangles but tests addition from one that tests triangles — a weaker
  leak of the same family that remains.
- **Existing bad rows stay in the table.** Serving is protected; the audit
  script is how they get cleaned up. No production write was made.

## Calibration against the live bank (2026-09-20, read-only)

The rules were run over all 1,036 rows before being wired in, then the flagged
rows and the tokens that carried the passes were read by hand.

- **Arithmetic topics (6) and Hebrew (13): not flagged by construction.**
- **Content topics: 42 of ~470 rows flagged (≈9%).** By class: bare `כמה זה
  A ⊕ B?` computations (15); "divide these into N equal groups" grouping
  exercises filed under time/data/gematria (9); number-line, `A + ___ = B`
  equation, and pick-the-operation exercises with no topic vocabulary or only
  data-story dress (13); skip-counting / cube-tower patterns (5, see false
  positives below).
- **Two calibration changes came out of it**, both in the *strict* direction:
  the bare-prefix match let "אותם" (them) satisfy gematria's "אות" (letter)
  and "קודם" satisfy length's "קו" — one real leak, "לפניך 15 כוכבים. חלקי
  אותם ל-3 קבוצות שוות", was passing on a pronoun. Anchors of ≤3 letters now
  must end the word (a plural allowed). And the generic verbs "התחיל/סיים"
  were dropped from the time vocabulary: they identify no topic, and removing
  them changed no verdict on the bank (7/3/0 flagged before and after).
  One change went the lenient way: survey wording ("ספרו", "תוצאות", …) was
  added to data, after the first pass flagged 20 of 30 `math-b-data` rows that
  are genuinely about polls.
- **Known false positives left in on purpose** (a rejected good row is only
  not served; a wrongly accepted one is the bug): four `math-g-multiplication-
  division` skip-counting patterns (10, 20, 30, … — arguably multiples, but
  indistinguishable by vocabulary from any other +N pattern) and one
  `math-b-geometry` tower-of-cubes pattern.
- **Known false negatives, stated:** survey-story exercises whose actual skill
  is a number line or a sum ("היכן נמצא המספר 5 … ילדים שנולדו בינואר") pass
  in data topics once they use survey wording. The check is about vocabulary,
  not about which skill is being tested; closing that needs a topic ↔ subtype
  compatibility rule, which is a product/pedagogy call and is not made here.
- **Anchor lists are hand-written from the Ministry's wording and tuned on the
  bank; they are the part most worth a curriculum owner's eye.**

# Pre-ship review (2026-09-21)

The fix was held back from the deploy that shipped Tasks 3/5/6 and reviewed
before shipping. Three questions were asked of it; all three found something.

## 1. Does the check wrongly reject good exercises? — Yes, 5 rows. Fixed.

Re-checked every row the audit flags. Five are genuinely about their topic:

- **Four skip-counting sequences** in `math-g-multiplication-division`
  ("10, 20, 30, …", "300, 600, 900, 1,200"). A run of multiples IS how the
  grade-ג curriculum reaches multiplication; they were rejected only for
  carrying no multiplication *word*. Fixed by accepting the
  `pattern_completion` subtype in that one topic. The topic holds exactly 4
  `pattern_completion` rows, so this admits those 4 and nothing else, and a
  bare sum there is still rejected.
- **One tower-of-cubes row** in `math-b-geometry`. `קובייה` is a solid — the
  anchor list simply had no 3D shapes. Fixed by adding
  קובייה/תיבה/כדור/גליל/חרוט/פירמידה/מנסרה to the geometry vocabulary.

Flagged rows: **42 → 37**. All six known genuine leaks stay rejected.

## 2. Do the unchecked Hebrew topics leak? — Yes, worse than math. Not fixed.

The check covers 22 of 35 topics; the 13 Hebrew ones are pass-through. They
were measured here for the first time, without needing anchors, by looking for
identical question text filed under more than one topic — at most one filing
can be right:

- **Hebrew: 23 questions appear under 2+ topics, covering 95 rows** (~24% of
  the 391 Hebrew rows). Math, for comparison: 11 questions / 30 rows.
- Worst case: `איזו מילה נגזרת מהשורש ק-ר-א?` is filed under **five** topics
  — early-writing, reading-fluency, literary-texts, reading-comprehension and
  vocabulary.
- The shape of the leak matches math exactly: all 13 Hebrew topics carry all 7
  Hebrew subtypes, so root-derivation and niqqud drills are spread across
  every topic regardless of what the topic is about
  (`hebrew-g-reading-comprehension` holds three copies of the same root drill;
  `hebrew-g-writing-process` holds grade-א niqqud).

This is a **lower bound** — it only catches exact duplicates. Hebrew is left
unprotected on purpose (see the limitation above: no reliable code-checkable
vocabulary), but the size of the gap is now a measured number rather than an
open question, and it is larger than the math leak this fix addresses.

## 3. Can the serving filter block legitimate content? — Not any more.

Two findings:

- **No (topic, level) bucket is emptied by the filter.** Serving draws per
  topic AND per adaptive level, so that is the pair that matters. Across all
  47 content buckets the smallest surviving pool is 3 (`math-b-time` L2, 3 of
  5); the heaviest drop is `math-a-data` L1 (5 of 10).
- **But the downstream failure mode was a 500.** The RPC also excludes rows
  the kid already attempted, so a pool CAN empty in a real session. The caller
  then generates, and admission can reject every draft — `TopicFitError` fell
  through to the route's generic `catch` and became HTTP 500, i.e. the child
  sees "משהו השתבש" and gets no exercise at all. That trades the off-topic
  exercise this check exists to prevent for something worse.

  Measured how likely that is, against the real generator: **12 live
  generations on the two worst buckets (`math-a-data` L1, `math-g-gematria`
  L1) — 12/12 served, 0 off-topic drafts rejected, 0 failures.** The
  post-2026-09-15 prompt and this check agree in practice, so the path is
  rare, not routine. Rare is not impossible, so it is now closed
  structurally: on a `TopicFitError` that survives every retry, the route
  re-queries the bank with the fit check off and serves that row — exactly
  what production served before this check existed — and saves nothing. If
  the bank is empty too, the error still surfaces. Every other generation
  failure is untouched.

## Still not addressed (unchanged by this review)

- Hebrew topics remain unchecked (quantified above).
- The check remains vocabulary-based: it cannot tell an exercise that mentions
  triangles but tests addition from one that tests triangles.
- **A prompt tension worth a follow-up, deliberately not changed here:** the
  `fill_in_blank` subtype guidance orders a bare computation and explicitly
  "not a word problem", while a resolved topic simultaneously demands topic
  content. Every bare-computation leak in the bank is a `fill_in_blank`. The
  good rows show the resolution — a one-clause topical preamble, then the
  computation ("בדיאגרמת העמודות… כמה זה 5 + 4 + 3?") — but the guidance does
  not ask for it. Changing generation wording is a bigger change than a
  pre-ship review should make.
- Existing off-topic rows stay in the table; serving is what protects kids.
